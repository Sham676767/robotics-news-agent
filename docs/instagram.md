# Instagram: черновик, одобрение и публикация

## Подключение

CLI читает `.env` **из текущей папки проекта** через python-dotenv, без поиска
родительских папок и без изменения окружения процесса. Уже заданные переменные
окружения имеют приоритет; Docker Compose передаёт `.env` через `env_file`.
Токены не принимаются аргументами команд, не сохраняются в черновики и не
попадают в repr/логи. Подписанные URL тоже не сохраняются и не выводятся.

В `.env` заполните `INSTAGRAM_USER_ID`, `INSTAGRAM_ACCESS_TOKEN`,
`INSTAGRAM_API_VERSION` в формате `vNN.N`: выберите версию, поддерживаемую
вашим приложением Meta. Версия намеренно не подставляется наугад.
По умолчанию `INSTAGRAM_LOGIN=instagram`, адрес — `graph.instagram.com`.
Нужен Business/Creator и токен с правом публикации. Для Instagram Login это
`instagram_business_basic` и `instagram_business_content_publish`.
Создание Meta-приложения, OAuth и получение токена выполняются вне этой CLI.

Для уже настроенного Facebook Login задайте `INSTAGRAM_LOGIN=facebook`:
используется `graph.facebook.com`, профессиональный Instagram связан с
Facebook Page; нужны соответствующие разрешения `instagram_basic`,
`instagram_content_publish`, `pages_read_engagement`. Токен должен относиться
к выбранному способу входа. Его действительность и доступы проверяет Meta
при реальном запросе, проверка формата этого не подтверждает.

## S3-совместимое хранилище

Реализованы интерфейс `VideoStorage` и `S3VideoStorage` на boto3. Настройки:

| Переменная | Назначение |
| --- | --- |
| `S3_ENDPOINT` | Адрес S3 API вашего провайдера |
| `S3_BUCKET` | Уже созданный бакет |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | Ключи с правами записи/чтения и удаления объекта |
| `S3_REGION` | Регион провайдера; для R2 обычно `auto`, для AWS/MinIO — выбранный регион |
| `S3_PUBLIC_BASE_URL` | Необязательный публичный корень URL для ключей объектов |
| `S3_PRESIGN_TTL_SECONDS` | Если публичного корня нет: срок подписанной GET-ссылки, по умолчанию 7200 секунд |
| `S3_DELETE_AFTER_PUBLISH` | Удалить объект после подтверждённой публикации; по умолчанию `true` |
| `S3_ADDRESSING_STYLE` | `auto`, `path` или `virtual`; для локального MinIO удобно `path` |

Адаптер допускает настраиваемые endpoint/region для R2, B2, Yandex Object
Storage и MinIO. Собственные тарифы, доступы и настройки бакета задаются у
провайдера; тесты адаптера выполняются на моках, подключения ко всем этим
облакам отдельно не подтверждались. ACL бакета программа не изменяет.

При пустом `S3_PUBLIC_BASE_URL` объект может оставаться приватным:
Instagram получает подписанный URL. Для публичного бакета `S3_PUBLIC_BASE_URL`
должен соответствовать **корню объектов**: например, для path-style URL
включать имя бакета. Добавление ключа должно давать прямую ссылку на MP4.
В ссылке для Instagram требуется публичный HTTPS на порту 443; локальный
MinIO подходит только для проверки S3. Фактическую доступность проверяет
загрузка со стороны Meta, локальная проверка URL проверяет лишь формат.

Загрузка происходит после одобрения и проверки квоты, до создания REELS.
Ключ объекта содержит ID черновика и SHA-256 видео, MIME — `video/mp4`.
URL не должен истечь во время обработки. Короткий TTL отклоняется до
создания контейнера. После успеха сначала надёжно записывается результат,
затем удаляется объект. Ошибка удаления даёт `cleanup_pending: true`;
повторный `publish ID` повторяет только очистку, не публикацию.

## Последовательность команд

```bash
docker compose build
# Только проверка и план: без сети, платных запросов и новых файлов.
docker compose run --rm agent python -m app run-all --dry-run

# Обычный запуск платных сервисов: один ролик на одну выбранную тему.
docker compose run --rm agent python -m app run-all --count 1

# После просмотра всего комплекта и ручной юридической проверки:
docker compose run --rm agent python -m app approve reel-ID

# Проверка уже одобренного комплекта без загрузки/публикации:
docker compose run --rm agent python -m app publish reel-ID --dry-run

# Реальная загрузка в S3 и публикация в Instagram:
docker compose run --rm agent python -m app publish reel-ID
```

Замените `reel-ID` полным ID из результата. `run-all` завершает работу на
состоянии `awaiting_approval`. `approve` фиксирует только ручное одобрение,
`publish` — отдельное действие. Одобрение привязано к контрольным суммам всех
материалов, выбранному аккаунту и `INSTAGRAM_SHARE_TO_FEED`. Изменение любого
материала требует пересборки и нового одобрения; не редактируйте служебные
контрольные суммы или статусы вручную.

Если материалы уже созданы на предыдущих этапах, соберите их без повторной
генерации:

```bash
python -m app prepare --input drafts/reel-script-ID.json \
  --timings audio/tts-ID/timings.json --video renders/render-ID/video.mp4
```

Черновик в `drafts/reels/reel-ID/` содержит `script.json`, `script.review.json`,
`sources.json`, `caption.txt`, `audio.wav`, `timings.json`, `video.mp4`,
`render.json`, `subtitles.ass`, `draft.json` и `state.json`. В `run-all`
сохраняется также `topic.json`, отчёт сбора — в `drafts/runs/`. Финальная
подпись состоит из проверенной caption, дисклеймера и хэштегов. Новые правовые
утверждения не добавляются; ссылки остаются в видео и `sources.json`.

`draft.json` описывает комплект и проверку, `state.json` — одобрение и
состояние публикации. Исходный аудит LLM продолжает содержать
`publication_allowed: false`: он сам не выдаёт разрешение. Разрешением
служит отдельное ручное одобрение конкретного комплекта. При ошибке этапа
сохраняются уже полученные материалы и имя проваленного этапа. При отклонении
сверки черновик получает `quarantined`, TTS и рендер не запускаются.

Команды не отмечают тему использованной автоматически: сохранена согласованная
отдельная команда `mark-used`. Обычный `run-all` вызывает внешние сервисы и
может тратить их баланс. `--count` задаёт 1–10 роликов, каждый по одной теме.

## Dry-run и локальные заглушки

`run-all --dry-run` проверяет форматы и наличие ключей, источники, шаблон,
FFmpeg/ffprobe, фильтр libass, установленный шрифт через `fc-match` и права
доступа к папкам. Он не создаёт папки, черновики, объекты S3, записи истории
или клиент API. Существующая история читается только в режиме SQLite `ro`
для оценки объёма дедупликации. Результат — JSON со списком проблем, планом,
моделью, голосом, количеством роликов и оценкой платных запросов; код 0 при
готовности, 2 при проблемах. Проверка доступа к папкам основана на правах,
без пробной записи. Действительность ключей, квоты и деньги без сети неизвестны.

Оценка запросов разделяет генерацию, сверку, TTS и верхнюю оценку смысловых
сравнений с учётом сохранённой истории. Учитывается максимум ретраев; число
запросов не является оценкой денежной стоимости. Публикационные запросы
указаны отдельно как следующий шаг после ручного одобрения.

```bash
# Настоящий MP4 без внешних API и без платной генерации:
docker compose run --rm agent python -m app run-all --stub
# Или PIPELINE_MODE=stub в .env.
# Проверка только локальной готовности режима заглушек:
docker compose run --rm agent python -m app run-all --stub --dry-run
```

Stub использует фиксированный учебный текст с явно вымышленными реквизитами,
тихий тон 440 Гц длительностью 30 секунд, оценочные тайминги и настоящий
FFmpeg-рендер. С финальным экраном по умолчанию получается 33 секунды.
Заголовок видео явно сообщает, что это тест. Источники не скачиваются,
история не меняется. **Stub нельзя одобрить или опубликовать**, даже если
переключить `.env` обратно в live. Проверка с `local-stub` не принимается
за настоящую проверку и при импорте через `prepare`.

## Ретраи, квоты и восстановление

Graph API: `POST /IG_ID/media` с `media_type=REELS`, `video_url`, caption;
затем `GET /CONTAINER_ID?fields=status_code`; при `FINISHED` —
`POST /IG_ID/media_publish` с `creation_id`. Токен передаётся только в
Authorization Bearer. HTTP-редиректы не выполняются. Проверка
`content_publishing_limit` читает квоту из ответа, не фиксирует число постов
в коде. Повторяется перед финальной публикацией.

Временные ошибки и ограничения запросов используют экспоненциальную паузу
в пределах `INSTAGRAM_MAX_ATTEMPTS`. `Retry-After` не сокращается: слишком
длинная пауза сохраняется до следующего запуска. Ошибки токена, прав и
ограничения аккаунта не повторяются. S3 использует стандартный режим
экспоненциальных ретраев boto3 с тем же ограничением числа попыток.

Опрос по умолчанию — до 5 проверок с паузой 60 секунд, настраивается.
`processing_pending` позволяет повторить `publish` с тем же контейнером без
повторной загрузки. `ERROR`/`EXPIRED` сохраняют причину и требуют выяснить
проблему/подготовить новый черновик. Исходный объект до подтверждённой
публикации автоматически не удаляется: его можно убрать после ручного разбора.

До `media_publish` сохраняется состояние `publishing`. Если ответ потерян,
сервер вернул 5xx или процесс прервался, следующий `publish` **только сверяет
статус старого контейнера**. `PUBLISHED` фиксирует успех без второго POST.
Если ID опубликованного media не был получен, он остаётся `null`, не
выдумывается. При неопределённом результате остаётся `publish_unknown`:
проверьте сам Instagram; повторный POST автоматически не выполняется.
Если подтверждено, что поста нет, можно подготовить новый комплект через
`prepare` и отдельно одобрить его. Не делайте этого до проверки аккаунта.

Операции одобрения/публикации сериализованы SQLite-блокировкой папки
черновиков. Аварийное завершение освобождает блокировку, состояние записывается
атомарно. Два независимых хранилища черновиков не координируются между собой:
для одного аккаунта используйте одну общую папку проекта.

## Локальный MinIO

Пошаговый запуск приведён в README. `docker-compose.minio.yml` поднимает
изолированную проверку на `127.0.0.1:9000` и консоль на `127.0.0.1:9001`.
Образ собирается из фиксированного исходного релиза MinIO для локальной совместимости;
публично этот тестовый сервер не открывайте. Community-репозиторий MinIO
архивирован, поэтому для рабочего публичного хранилища выберите поддерживаемое
развёртывание/провайдера. `scripts.check_minio` ограничен локальными адресами,
загружает один тестовый объект, читает по подписанному URL, сравнивает SHA-256
и удаляет этот объект. Instagram в этой проверке не вызывается.

## Проверки и источники API

```bash
python -m pytest -q
docker compose run --rm agent sh -c 'python -m pip install -r requirements-dev.txt && python -m pytest -q && python -m pip check'
```

Внешние API в тестах заменены моками. Отдельный интеграционный тест запускает
stub и проверяет реальный MP4 через ffprobe. Для публикационного адаптера
проверены успешный путь, лимиты, ошибки токенов, таймауты, polling, очистка,
повторные запуски и отсутствие второго `media_publish` при неопределённом ответе.
